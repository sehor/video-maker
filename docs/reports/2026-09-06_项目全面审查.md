## 结论

项目已具备较完整的**模拟视频生成控制面**：认证、项目与镜头、报价、双分录秒数账本、批次原子冻结、任务状态机、Outbox、取消、回调、重试、恢复和媒体校验均有实现与测试。尚不能作为已完成的真实视频 SaaS 验收。

本次发现 **3 项 P1、5 项 P2**。P1 涉及文件丢失、已提交任务的输入发生变化，以及响应丢失后的重复任务与重复消费。应先修复这些问题，再进入真实路线验收。未发现可据本次证据定为 P0 的问题；这不代表所有故障和并发组合都已穷尽。

## 一、按优先级排列的发现

### F1 · P1：重复写入同一个 Storage Claim 会删除已有文件

- 位置：`apps/api/app/storage.py:352`，`LocalObjectStorage._put_bytes`。
- 触发：同一个未过期 write claim 成功写入后，再次执行 `put`。
- 原因：`path.open("xb")` 因文件已存在抛出 `FileExistsError`；通用异常处理随后执行 `path.unlink(missing_ok=True)`，把之前成功保存的文件删除。上层虽然返回 `STORAGE_OBJECT_EXISTS`，实际已破坏原对象。
- **实测**：第一次写入成功；第二次返回上述冲突；随后 `stat` 返回 `STORAGE_OBJECT_NOT_FOUND`。
- 影响：存储重试或重复投递可能造成素材、视频数据丢失，破坏不可变对象语义。
- 建议：区分“本次创建后写入失败”与“目标原本存在”；只有本次创建的临时/目标文件才允许清理。为所有 Storage 适配器增加重复写入后原内容保持不变的契约测试。

### F2 · P1：Job 没有冻结创作输入，排队或重试期间会改用新内容

- 位置：`apps/api/app/provider_execution_context.py:67`、`:71`、`:90`；`apps/api/app/public_api.py:379`、`:423`。
- 原因：执行上下文每次查询当前 `Shot.prompt` 和当前 `ShotReference`，没有读取 Job 创建时的输入快照。镜头修改和解绑接口允许在任务存续期间继续操作。
- **实测一**：提交 Job 后修改镜头提示词，未执行的 Job 读取了修改后的提示词。
- **实测二**：提交带参考图的 Job 后解绑参考图，该 Job 的 `reference_object_key` 变成 `None`。
- 影响：生成内容与用户提交时的意图不一致；重试可能变成另一个生成请求；要求参考图的路线可能因事后解绑而失败。报价快照只锁住计价参数，不能代替执行输入快照。
- 建议：在创建 Job 的事务中持久化提示词、素材对象/版本及必要生成参数；所有 Attempt 和重放读取该快照。素材生命周期同时考虑被活跃 Job 快照引用的情况。

### F3 · P1：前端对“服务端接受、响应丢失”的恢复会新建第二个收费任务

- 位置：`apps/web/app/pages/projects/[id]/shots/[shot_id].vue:11`；`apps/web/app/composables/useApi.ts:11`。
- 触发：第一次生成已被服务端接受，响应因断网丢失；用户看到错误后再次点击“开始生成”。
- 原因：每次点击都重新申请 Quote，且 API 封装每次生成新的 `Idempotency-Key`。服务器看到的是新 Quote、新请求，无法把它识别为上一次提交的恢复。
- **前端脚本隔离复现**：模拟第一次任务已接受但响应丢失，连续两次调用实际页面的 `generate`，得到 `quotes=2`、`acceptedJobs=2`。此验证使用模拟 API，没有发生真实消费。
- 影响：用户为同一次意图产生两个 Job；两者成功时分别结算。后端“每个 Job 只结算一次”不能防止这种问题。
- 建议：为一次用户操作保存稳定操作 ID、Quote 和提交幂等键；结果不明时先恢复/查询原操作，明确发起新生成时再创建新键。页面刷新后的恢复也应有方案。

### F4 · P2：项目没有绑定路线版本，全局路线切换会改变同项目后续生成

- 位置：`apps/api/app/public_api.py:155`、`:707`、`:771`；`apps/api/app/models.py:177`。
- 总纲要求 Project 绑定具体路线版本，但 Project 模型没有此绑定，单任务和 Batch 都选择全局 active route。
- **实测**：同一 Project/Shot 第一次使用 `mock_video_v1`，切换全局路线后第二次使用 `runpod_simulated_v1`，两次 Job 的 candidate ID 不同。
- 影响：Job 自身记录了路线，已有 Job 不会因此被改写；但是同项目后续镜头的一致性没有保证。这与总纲的项目级版本绑定要求不同。
- 建议：将项目路线绑定持久化，明确首次绑定、显式升级和停单的规则；全局默认路线用于新项目选择。

### F5 · P2：项目删除清理遗漏 Provider 原始视频对象

- 位置：`apps/api/app/artifacts.py:94`；`apps/api/app/project_cleanup.py:73`。
- 原因：远端接收流程从 `provider-outputs/{job}/{attempt}/...` 复制生成最终 `outputs/{job}/...`，但项目清理只枚举 `ProjectAsset` 和 `GenerationOutput`。原始 Provider 对象没有进入清理清单。
- **实测**：远端产物成功校验、发布并结算后删除项目，Cleanup Outbox 已标记发布，原始 Provider MP4 仍存在。
- 影响：项目删除并未覆盖全部产物，存储空间持续增长，也无法完整兑现项目素材清理语义。
- 建议：持久化 Attempt 原始产物对象，明确成功、失败、迟到结果和删除项目时的保留期限与清理责任；清理必须可重试且不影响回调重放。

### F6 · P2：前端上传参考素材后没有绑定到镜头

- 位置：`apps/web/app/pages/projects/[id]/index.vue:20`；`apps/web/app/pages/projects/[id]/shots/[shot_id].vue:15`。
- 原因：上传只调用 Project Asset 接口并显示文件名。当前页面没有调用 `/shots/{id}/references`，也没有素材选择、绑定和恢复已有素材的界面。
- 影响：普通用户通过当前 UI 上传的图片不会自动成为生成输入。Mock 不要求参考图，现有 E2E 因此能通过；切换到要求 input claim 的模拟 I2V 路线后，仅通过 UI 无法完成必需的绑定步骤。
- 证据类别：当前页面与执行上下文的静态调用链核对；未将现有 E2E 误称为 I2V 用户闭环验收。
- 建议：补齐素材列表、镜头绑定和解绑；E2E 验证所选素材最终进入提交 claim，不能只检查上传返回 201。

### F7 · P2：PATCH 接受显式 null，却在数据库层变成 500

- 位置：`apps/api/app/schemas.py:38`、`:63`；`apps/api/app/public_api.py:379`。
- 原因：更新模型将非空数据库字段声明为可空；`exclude_unset=True` 会保留显式传入的 null，随后直接赋给 ORM 非空列。
- **实测**：`PATCH /v1/shots/{id}`，请求体 `{"prompt": null}` 返回 500，而不是可处理的 422。
- 影响：公开接口契约和数据库约束不一致；Project name、Shot title/duration/aspect 等同类字段也存在相同设计问题，其中本次实际 HTTP 复现的是 prompt。
- 建议：区分字段缺省与显式 null；仅真正可清空的字段允许 null，其他字段在请求验证阶段拒绝。

### F8 · P2：任务详情一次网络异常就永久停止轮询

- 位置：`apps/web/app/pages/jobs/[id].vue:17`。
- 原因：下一轮 `setTimeout` 只在本次请求和下载均成功后安排，异常时没有重试或状态恢复。
- **前端脚本隔离复现**：让实际 `load` 中的 API 请求发生一次临时错误，下一轮定时器调用次数为 0。
- 影响：服务端任务继续执行，页面停留在旧状态；失败时页面也不会给出可恢复的轮询提示。
- 建议：显式处理网络错误，使用有界退避重试并保留用户可见状态；在组件卸载时取消请求和定时器。下载失败的恢复应独立于 Job 状态轮询。
