# 模拟控制面故障恢复 Runbook

> 适用状态：`SIMULATION_ACCEPTED`。本 Runbook 只覆盖离线模拟控制面，不代表真实
> RunPod、GPU、对象存储、网络或 Hatchet 已验证。

## 通用预检

1. 请求 `/healthz`：失败表示 API 进程不可用。
2. 请求 `/readyz`：503 时按响应中的 `database`、`migrations`、`storage`、`workflow`
   分项定位依赖。
3. 使用管理员身份读取 `/v1/admin/operational-metrics`，记录
   `pending_count`、`oldest_pending_age_seconds`、`retry_count`、
   `dead_letter_count` 和 `stuck_job_count`。
4. 对单个 Job 读取 `/v1/admin/generations/{job_id}`，核对 Job、当前 Attempt、
   Provider Job ID、失败码和更新时间。
5. 不直接修改 Job 终态、Output 或账本；恢复动作必须复用 dispatcher、Reconciler 或
   Dead Letter 重放入口。

## Job 卡在 `SUBMITTING`

可能原因：submit 结果未知、Provider 已接收但响应丢失、进程在保存 Provider Job ID 前退出。

1. 核对 Attempt 的 `provider_job_id`、提交幂等键和最近 Job Event。
2. 保持 Reconciler 启用（`RECONCILER_ENABLED=true`），等待超过
   `RECONCILER_STUCK_AFTER_SECONDS` 后重新进入 Generation 执行入口。
3. 不创建新的业务 Job，不手工补 `SUBMITTED`。同一 Attempt 必须先通过 polling 对账；
   只有现有重试预算明确允许时才创建新 Attempt。
4. 验证最终只有一个 Output，且 `SETTLE`／`RELEASE` 互斥并各最多一次。

## Job 卡在 `CANCEL_REQUESTED`

可能原因：Cancel Outbox 未领取、租约持有者崩溃、Provider 已接受但响应丢失。

1. 核对绑定 Job／Attempt 的唯一 Outbox 事件及稳定键
   `attempt:{attempt_id}:cancel:v1`。
2. 保持 Outbox dispatcher 启用（`OUTBOX_DISPATCHER_ENABLED=true`）；租约过期后事件可重领。
3. 临时错误由 dispatcher 按重试策略处理；达到 `OUTBOX_MAX_ATTEMPTS` 后转入 Dead Letter。
4. Cancel 与成功竞态时，以统一完成路径的数据库结果为准；存在有效成功 Output 时结算，
   已确认取消且无有效 Output 时返还。

## Outbox Dead Letter

1. 使用管理员身份查询 `/v1/admin/dead-letters?status=OPEN`，保存来源类型、来源 ID、
   原始 payload、最后错误和尝试次数。
2. 先修复可验证的根因；不要修改 Dead Letter payload。
3. 显式调用 `POST /v1/admin/dead-letters/{dead_letter_id}/replay`。
4. 查询 `/v1/admin/operation-audits?target_id={dead_letter_id}`，确认重放审计存在。
5. 重复调用 replay 必须幂等；若事件再次永久失败，同一 Dead Letter 增加 cycle，不能丢失历史。

## Storage 对象缺失或删除失败

1. 对生成结果核对受控对象 key、对象存在/非空/大小上限及 Provider 媒体元数据；对象缺失不得发布或结算。
2. 对项目清理核对 `storage_cleanup_events` 及逐对象结果。对象已不存在视为幂等成功；
   临时删除失败保留错误并重试，已成功对象不得重复造成副作用。
3. 清理达到重试上限时按 Dead Letter 流程处理。
4. Project 保持软删除；不得因对象问题硬删除 Job、Attempt、Event、Output 或账本历史。

## 账本对账异常

对同一 `job_id` 检查：

- `RESERVE` 与业务报价秒数一致；
- `SETTLE` 和 `RELEASE` 不能同时存在；
- 两类终局分录各最多一条；
- 每个 Ledger Transaction 的借贷 Posting 平衡；
- Batch 中每个 Job 独立完成，不因部分失败重复结算或返还。

发现不变量破坏时立即停止新接单并保留数据库快照、Job Event、Attempt、Outbox 和审计证据。
当前仓库没有自动修账入口；不得用临时 SQL 改写不可变分录，应另立修复 Issue 和受审计的
调整分录方案。

## 恢复完成判据

- `/readyz` 返回 200；
- 对应 pending／stuck 指标恢复且没有新增未解释 Dead Letter；
- Job 达到合法终态；
- 最终 Output 数量不超过 1；
- `SETTLE`／`RELEASE` 互斥且各最多一次；
- 重放、重启或再次运行 Reconciler 不产生新业务副作用。
