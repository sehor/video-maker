# 02｜阶段二：秒数账本与可靠任务

> 目标：仍用 Mock Provider，把 Quote、余额、Batch、长任务、重试、结算和返还做正确。  
> 前置：阶段一验收通过；字段与状态机见 `90_核心数据模型与接口契约.md`。

## 1. 交付范围

- 数据库驱动的 Quality Tier、价格版本和不可变 Quote Snapshot；
- 按质量档分单位、以整数毫秒计量的双分录账本；
- Job／Batch 创建与秒数冻结同事务完成；
- Transactional Outbox 启动 Hatchet；
- Job／Attempt 状态机、幂等回调、有限重试和失败返还；
- Batch 原子冻结；
- 并发、重放、崩溃恢复和对账测试。

## 2. Quote 与账本

MVP 可配置：

```text
FAST：720p enabled
STUDIO：720p enabled；1080p disabled
CINEMA：无真实路线前 disabled
```

Quote 保存 `tier`、价格版本、时长、variant、分辨率、应冻结毫秒数和过期时间。提交时必须校验用户、未过期、未使用、参数一致和 Tier 可用；后台改价不能改历史 Job。

账本单位示例：`FAST_MS`、`STUDIO_MS`、`CINEMA_MS`，不得隐式互换。账户至少有：

```text
USER_AVAILABLE / USER_RESERVED
PLATFORM_ISSUED / PLATFORM_CONSUMED / PLATFORM_EXPIRED
```

发放、冻结、结算和返还都写平衡分录；`ledger_postings` 不可变，`wallet_balances` 只是事务内更新的余额投影。余额锁使用 `SELECT ... FOR UPDATE` 或等效机制，禁止浮点数和直接改余额字段。

## 3. Job 创建与 Outbox

在一个 PostgreSQL 事务内：

```text
锁定余额 → 校验 Quote → 写交易与分录 → 更新余额投影
→ 创建 Batch／Job → 保存 Quote Snapshot → 写 Outbox → commit
```

禁止“先建 Job，稍后异步扣余额”。

Outbox dispatcher 使用稳定幂等键启动 Hatchet，例如：

```text
generation-job:{job_id}:v1
```

即使“Hatchet 已接受但 Outbox 尚未标记”时进程崩溃，重复发布也不能创建第二个业务工作流。

## 4. Hatchet 边界

PostgreSQL 是业务真相；Hatchet 只负责编排、等待、重试和恢复。按至少一次执行设计：

- durable parent 只做确定性分支、等待和派生任务；
- DB 写入、Provider submit／cancel、R2 操作、结算和返还放在幂等 child task；
- 幂等由数据库唯一约束和条件更新保证，不能只靠应用内 `if`。

核心键：

```text
job:{id}:route:v1
job:{id}:settle:v1
job:{id}:release:v1
attempt:{id}:submit:v1
attempt:{id}:complete:v1
attempt:{id}:publish:v1
```

## 5. 重试、Batch 与取消

只自动重试临时基础设施错误，如网络超时、Provider 5xx、容量、队列超时和 Worker 中断。策略拒绝、非法输入、不支持参数、许可证阻止和确定性 workflow 错误不重试。

MVP 建议上限：每个 candidate 最多 2 次 Attempt，一个 Job 最多 3 次，并设置总时长和成本上限。

Batch 先整体 Quote，再一次性冻结总额；余额不足或任一 Quote 失效时全部失败，不能部分创建。执行后各 Job 独立结算或返还。

取消语义：

- 提交 Provider 前可可靠取消并返还；
- 提交后只做 best-effort cancel；
- Provider 未确认终止前不立即返还；
- 最终无有效输出才返还一次；
- UI 区分“取消请求中”和“已取消”。

## 6. 管理与测试

最小内部能力：查看 Job 全部事件、受控重试、测试秒数发放、强制释放异常冻结。所有管理员动作必须有理由、审计记录，并通过正常账本交易完成。

自动测试至少覆盖：

1. 多请求竞争同一余额；
2. Outbox 发送前和发送后崩溃；
3. submit 返回前连接断开；
4. Provider 重复、乱序、迟到回调；
5. polling 与 webhook 同时完成；
6. Hatchet worker 在关键 step 后重启；
7. settle／release 重放；
8. Job 成功后收到旧 Attempt 通知；
9. Batch 部分成功、部分失败。

## 7. 实施顺序

1. Tier、价格版本和 Quote Snapshot；
2. 双分录与余额投影；
3. reserve／settle／release 并发安全；
4. Job／Attempt 完整状态机；
5. Outbox 与 dispatcher；
6. Hatchet 和幂等 child task；
7. 错误分类、有限重试和取消；
8. Batch 原子冻结；
9. 崩溃、重放、并发和对账测试。

## 8. 验收门槛

- [ ] 并发提交不会超扣或产生负可用余额；
- [ ] 每笔余额变化都有平衡分录；
- [ ] Job、冻结和 Outbox 同事务提交；
- [ ] API／dispatcher／Hatchet 重启不会丢 Job；
- [ ] 重放不会重复 submit、settle 或 release；
- [ ] 只有临时错误创建新 Attempt；
- [ ] Batch 不会部分冻结；
- [ ] 已提交 Provider 的取消不会提前无条件退款；
- [ ] 所有测试仍不产生真实 GPU 成本。
